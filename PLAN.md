# PLAN — web-stealth

План реализации. Основан на [DESIGN.md](DESIGN.md); решения ниже зафиксированы,
спорные точки помечены как **ОТКРЫТО**.

## 0. Зафиксированные решения

| # | Решение |
|---|---|
| D1 | Прокси `socks5h://<host>:<port>`, без авторизации. **Только `socks5h`** — `socks5` ломается на IPv6 |
| D2 | `nodriver 0.50.5`. **Правка байта на чистой установке не нужна** — wheel из регистра чист, `import nodriver` проходит. `fix_nodriver.py` оставлен как дешёвая страховка: он идемпотентен и ничего не делает, если файлов с `0xb1` нет |
| D3 | Один браузер, одна вкладка, ленивый старт, idle TTL. Больше ничего не крутим |
| D4 | Tier 1 — `curl_cffi 0.16.3`, цель `chrome150`, заголовки переписаны под реальную систему (X11 Linux, Chrome 153) |
| D5 | Никакой подделки устройства и ротации профилей. Эмуляция — только геолокация и время: **Стокгольм** |
| D6 | Cookies: один раз харвест из браузера через прокси, дальше работаем с этим набором. Продление **по факту** сбоя |
| D7 | Выход: арендованный; адрес, город и ASN в репозиторий не выносятся |

Проверено, что переопределение заголовков не ломает отпечаток: с `chrome150`
и подменёнными `user-agent` / `sec-ch-ua` / `sec-ch-ua-platform` ответ
`200 h3`, TLS-слой остаётся chrome150.

**A1 закрыт:** `Accept-Language: en-US,en;q=0.9` на обоих уровнях.

**ОТКРЫТО A2 — какие origin'ы имеют право пользоваться jar'ом не из браузера.**
Сессия рождается в Brave (харвест), а дальше те же cookies уходят в `curl_cffi`
с TLS-отпечатком Chrome 150. Сайт, который коррелирует сессию между запросами,
видит, что клиент внутри одной сессии сменился. Варианты политики на origin:

| Политика | Смысл | Риск |
|---|---|---|
| `curl_only` | браузер не используется никогда | сессия всегда один клиент; нет JS-рендеринга |
| `curl_then_browser_jar` | браузер-резерв работает с теми же cookies | две подписи у одной сессии |
| `curl_then_browser_anon` | браузер-резерв без jar | сессия не светится, но браузер видит гостевой вид |
| `browser_first` | сразу браузер, curl не трогает origin | сессия всегда Brave; дорого по памяти |

Решение можно не угадывать, а измерить на M2 (см. раздел 9).

## 1. Архитектура

```
web_fetch(url) ──► seam provider ──► sidecar (Python)
                                      │
                        ┌─────────────┴──────────────┐
                   curl_engine                  browser_engine
                   chrome150 + jar + socks5h    nodriver 0.50.5, 1 вкладка
                        │                             │
                   classifier ──► повтор/эскалация ────┘
                        │
                     extract ──► text + links
```

Браузерные команды модели идут мимо seam, напрямую в sidecar теми же `op`'ами.

## 2. Компоновка

профильных путей в YAML не появляется.

## 3. Cookie-контур

Формат — как в [cookie_manager.py:78-90](cookie_manager.py#L78-L90):
`name, value, domain, path, expires, httpOnly, secure, sameSite, partitionKey`.
Один именованный набор на группу origin'ов, без пула и cooldown:

```
jar/google.json   jar/github.json   jar/brave.json
```

- **harvest:** `python -m fetchd.harvest` поднимает Brave через `socks5h`,
  открывает google/github/brave, ждёт ручного логина, снимает
  `cdp.storage.get_cookies()` и пишет наборы с фильтром по домену.
- **загрузка в браузер:** `cdp.storage.set_cookies(CookieParam…)` — как в
  [cookie_manager.py:189-211](cookie_manager.py#L189-L211).
- **обратно в jar:** после успешного ответа tier 1 сливать `Set-Cookie` в файл.
- **продление по факту:** классификатор помечает набор `stale`, следующий вызов
  возвращает явный текст «нужен ручной harvest», а не тихий повтор.
- Права `0600`, вне репозитория, значения не попадают ни в логи, ни в вывод.

## 4. Fingerprint-контур (один на оба уровня)

Единый источник — `config/fp.json`:

| Поле | Tier 1 (`curl_cffi`) | Tier 2 (nodriver) |
|---|---|---|
| UA / UA-CH | заголовки: X11 Linux, Chrome 153 | не трогаем (реальный Brave) |
| `Accept-Language` | заголовок | **не трогаем** (реальный браузер) |
| Геология | нет аналога | `Emulation.setGeolocationOverride` + `setTimezoneOverride("Europe/Stockholm")` |
| TLS/HTTP2 | `chrome150` | как есть |

`generate_hardware_script`, `DEVICE_PROFILES`, `set_user_agent_override`,
`set_device_metrics_override`, touch и ротация — **не используются**.

```
→ {"op":"fetch","id":N,"url":"...","maxChars":12000,"timeoutMs":45000}
→ {"op":"raw","id":N,"url":"...","maxBytes":60000}
→ {"op":"search","id":N,"query":"...","maxResults":8}
→ {"op":"browser.open","id":N,"url":"..."}
→ {"op":"browser.state","id":N}
→ {"op":"browser.find","id":N,"text":"..."} | {"selector":"..."} | {"xpath":"..."}
→ {"op":"browser.links","id":N,"filter":"..."}
→ {"op":"browser.act","id":N,"index":12,"action":"click|type|scroll","value":"..."}
→ {"op":"browser.eval","id":N,"js":"...","awaitPromise":true}
→ {"op":"browser.close","id":N}
→ {"op":"jar.status","id":N}
→ {"op":"cancel","id":N} {"op":"shutdown"}
← {"op":"ready",...} {"id":N,"ok":true,"data":{...}} {"id":N,"ok":false,"error":{...}}
```

Коды ошибок дополнить: `jar-stale`, `challenge`, `geo-blocked`.

Поиск элемента: `text` → `find_all` (поиск по DOM, дёшево), `selector` →
`select_all(include_frames=True)`, `xpath` → `xpath()`. Разделение явное,
потому что `find_all` селекторы не понимает.

## 7. Память и конкурентность

- Мьютекс на все браузерные операции; параллельно — только `curl_engine`, не
  больше 3 запросов.
- Idle TTL браузера 90 с, затем `stop()`. Доступно 3.7 GiB.
- `fetchTimeoutMs` в ряду `tool-web` поднять до 90 000: браузерный рендер не
  влезает в дефолтные 30 000.

## 8. SSRF

С `socks5h` адрес резолвит **прокси**, а не наша машина, поэтому сценарий
«публичный хост резолвится в `127.0.0.1`» к нам не попадает — его разрешает
xray. Остаётся только литеральный IP в URL, и он уже отклоняется
[policy.js](web-stealth/lib/policy.js). Решение: **блок оставляем** как дешёвую
страховку, отдельный allowlist не делаем.

## R41 — заголовки запроса: сравнение и эксперимент (закрыто как измерение)

Захвачено `Network.requestWillBeSentExtraInfo` — единственный честный источник: Chrome дописывает заголовки сам, после того как страница попросила. Значения cookie в дампе заменяются размером (`<1786 bytes, 4 pairs>`), `authorization`/`set-cookie` вычёркиваются: вопрос был в именах и форме, а не в секретах.

Ловушки nodriver, найденные на живом прогоне: `get_response_body` требует `cdp.network.RequestId(...)`, а не строку (иначе `AttributeError: 'str' object has no attribute 'to_json'`); тело живёт, пока браузер держит ресурс — после навигации это `ProtocolException: No resource with given identifier found`, поэтому заголовки теперь отдаются и без тела.

Различия браузера и curl-половины (браузерный документный запрос против того, что увидел httpbin):

| заголовок | браузер | curl-половина |
|---|---|---|
| `accept` | без `application/signed-exchange` | профиль chrome150 по-прежнему шлёт `signed-exchange;v=b3` |
| `accept-language` | `en-US,en;q=0.5` | `en-US,en;q=0.9` |
| `accept-encoding` | `gzip, deflate, br, zstd, dcb, dcz` + `available-dictionary` | без dcb/dcz |
| `sec-gpc` | `1` | отсутствует |
| high-entropy hints | arch/bitness/full-version-list/model/platform-version/wow64 | отсутствуют |
| `priority` | `u=0, i` | `u=0, i` — совпадает |

Эксперимент: тот же SERP-запрос через curl-половину с браузерными `accept` и `accept-language`. Ответ **не изменился** — в обоих прогонах страница «If you're having trouble accessing Google Search». Значит стена не в этих заголовках. Остаются TLS/JA4 (слои HTTP/2 уже совпадают) и токены словарей, которые curl не умеет. Добавлены ручки `STEALTH_ACCEPT` и `STEALTH_SEC_GPC`; `accept` берётся из наблюдаемого отпечатка, если он снят.

## R42 — форма google-запроса из реального Chrome (закрыто как измерение)

Проверены три формы через curl-половину на своём jar: `/search?q=…&hl=en`, та же с `oq`+`sourceid=chrome`, и с добавлением `source=chrome.ob`. Все три — одна и та же мягкая стена, ноль результатных ссылок. Форма URL роли не играет.

Побочное: язык страницы стены следует локали выхода, а не запросу — без `hl` Хельсинки отдаёт финское предложение, с `hl=en` английское. Проверять «ответил ли движок» по фразе нельзя: нужен подсчёт результатных ссылок. Первый прогон дал ложное «answered» именно на этом.

Чего в нашем запросе нет и чем это не заменяется: `gs_lcrp` (сжатый привязанный к сессии набор параметров, его генерирует сама страница), `x-browser-validation`/`-channel`/`-year` (их считает кодовое окно Chrome), полный набор high-entropy hints (`sec-ch-ua-full-version`, `form-factors`, `prefers-color-scheme`, `downlink`, `rtt`) и взрослая подписанная сессия в cookie. Первое, что можно получить честно — снять `gs_lcrp` со своего браузера через `browser_requests` и повторить этот URL curl-половиной.

## R43 — где на самом деле стена, и живут ли переопределения CurlOpt (закрыто)

Эксперимент, который следовало сделать раньше остальных: взять **тот же** документный запрос, который делает наш браузер (URL с `sei`, те же cookie из jar, те же заголовки из `requestWillBeSentExtraInfo`), и повторить его curl-половиной. Браузер на этом запросе получает SERP 158 кБ, curl — страницу стены, 88 символов. Заголовки убраны из кандидатов, как и форма URL (R42), как и набор cookie: он у половин один и тот же.

Живёт ли переопределение поверх `IMPERSONATE` — проверено на `https://tls.peet.ws/api/tls`:
- база `chrome150`: `t13d1516h2_8daaf6152771_806a8c22fdea`
- база + `SSL_CIPHER_LIST`: `t13d516h2_e133e205ac38_806a8c22fdea` — хеш сдвинулся, значит ручка работает поверх профиля
- база + `TLS_EXTENSION_ORDER` со списком наугад: `curl: (35) Invalid TLS extension order` — формат строгий, значение надо подбирать

Разложение дельты: вторая секция JA4 (набор шифров) у половин **уже одинаковая** (`8daaf6152771`). Расходятся первая (16 против 17 расширений — браузер шлёт на одно больше) и третья (содержимое и порядок расширений). То есть чинить надо не шифры, а расширения; `TLS_EXTENSION_ORDER` для этого есть, но четырнадцатое предположение о формате не прошло.

Что это меняет: стена в транспортном отпечатке, и единственный способ её проверить — собрать у браузера список TLS-расширений и повторить его curl-половиной. Если лишнее расширение — ECH, бесплатного пути нет: конфиг ECH берётся из DNS-записи HTTPS, а не из настроек клиента.

## R44 — ветка JA4 закрыта: половины уже идентичны (закрыто, переворот)

Замер отпечатка **нашего** браузера на том же измерителе, что и curl-половина (`tls.peet.ws/api/tls`): JA4 `t13d1516h2_8daaf6152771_806a8c22fdea`. У curl-половины — тот же символ в символ. JA3 тоже совпал, слой HTTP/2 совпадал и раньше.

Прежняя таблица сравнивала curl с Chrome 155 владельца, а не с браузером плагина: отсюда и «расхождение TLS». Сравнивать надо было свои половины, и как только это сделано, ветка F1-TLS закрывается: при одинаковых JA3, JA4, Akamai и JA4T одна половина получает SERP 158 кБ, другая — стену 88 символов.

Значит стена не в TLS, не в HTTP/2, не в TCP, не в заголовках (R43) и не в форме URL (R42). Остается то, что curl воспроизвести не может в принципе: `accept-encoding: dcb, dcz` с `available-dictionary` (браузер объявляет поддержку структурированных словарей, curl — нет) и исполнение JS, после которого google ставит себе токен в ту же сессию. Обе причины не лечатся настройкой клиента, и обе объясняют, почему `js-proof` — честный ярлык для этой стены.

## R45 — подписанная сессия на стену не влияет (закрыто)

Собран настоящий вход в Google через интерактивный сбор (`fetchd.harvest --groups google`): в jar вместо 5 анонимных cookie стало 35, имена `LSID`, `OSID`, `ACCOUNT_CHOOSER`, `NID`, `APISID` — то есть сессия подписанная, а не полуанонимная. Тот же SERP через curl-половину: та же стена, 88 символов, ноль результатных ссылок.

Итог по всем кандидатам: форма URL (R42) — нет, заголовки (R43) — нет, TLS/HTTP2/TCP (R44) — половины идентичны, сессия и cookie — нет. Остаётся исполнение JS: google после скриптов ставит в сессию токен, которого у curl не будет никогда, плюс `dcb`/`dcz` со словарями, которых curl не умеет. Ярлык `js-proof` для этой стены — точный, а не вежливый.

Побочный результат, который остаётся в силе: google-половина jar теперь подписанная, и это работает в обратную сторону — вход, сделанный в браузерной половине, переезжает в jar и доступен curl-половине для всех остальных задач, где google не требует исполнения скриптов.

## R46 — поправка к R42 и одна конкретная находка (открыто)

Поправка: вывод R42 («форма URL не влияет») измерен на URL **без** набора токенов, которые google выдаёт сессии (`sca_esv`, `sxsrf`, `gs_lp`, `ei`, `sclient`). Наблюдение владельца это вскрывает: рабочий curl меняет только `q=`, токены остаются — значит они привязаны к сессии, а не к запросу, и их можно переиспользовать. Без токенов не помогает никакая форма — это и было измерено; наличие токенов не проверялось вообще.

Находка: в нашем jar 38 cookie, но **нет `DV`** — google-овского cookie проверки устройства, который выдаёт исполненный JS. В рабочем запросе владельца `DV` есть. Браузерная половина получает настоящий SERP (проверено на `q=apple`: выдача с результатами) по URL вообще без `sca_esv`, то есть токен-набор браузеру не нужен — он нужен скриптованному клиенту, чтобы выглядеть браузером.

Почему `fetch()` внутри страницы отдаёт 401, а curl снаружи — документ: fetch не является навигацией, у него другие `sec-fetch-*` и нет браузерных токенов, google такой запрос не считает переходом.

Не закрыто: чем именно google выдаёт `DV` нашей сессии — не выдан ли он потому, что браузер проходит проверку без вызова, или потому что вызов ещё не случался.

## R47 — стена снята: нужен омнибокс-жетон `gs_lcrp` (закрыто, переворот)

Запрос владельца без `DV`, но с `gs_lcrp` + `oq` + `sourceid=chrome` + `source=chrome.ob`, проигранный curl-половиной **на нашем jar**: настоящий ответ, и он же работает со подменённым `q=` (проверено на двух разных запросах — Cambridge по `chill`, DeepSeek по `deepseek`). Стена рушится не заголовками, не cookie и не TLS, а одним параметром URL.

Почему R42 этого не увидел: там были `oq` и `sourceid=chrome`, но не было `gs_lcrp`. Значит из набора решает именно он. `DV` не обязателен (запрос без него проходит). `x-browser-*` не обязательны: curl-половина их не слала.

Что это значит: `gs_lcrp` не привязан ни к запросу, ни к сессии — чужой жетон работает с нашими cookie. Внутри него base64 protobuf, начало `EgZjaHJvbWU` читается как «chrome», дальше счётчики и история набора. Он генерируется омнибоксом Chrome при поиске прямо из адресной строки, поэтому ни наша браузерная половина (ходит по URL), ни curl его не производят.

Открыто: где взять свой жетон. Варианты — снять его из омнибокса нашего браузера (нужно, чтобы в адресной строке набрали запрос руками) или собрать жетон самому, разобрав protobuf. Второе проверяемо без внешних данных.

## R49 — жетон не проверяют: достаточно его наличия (закрыто, решает всё)

Снят настоящий жетон: в Chrome (155.0.8059.39, тот же, что у владельца) омнибокс выдал `gs_lcrp=EgZjaHJvbWU…` на запрос «github». Проверка через curl-половину на нашем jar, три случая:

|---|---|

## R57 — PDF читаются curl-половиной (закрыто)

Раньше оба пути отказывали: curl — по типу содержимого, браузер — с нулевым извлечением текста, при этом поисковая половина цитировала цифры из тех же файлов. Замерен независимо, FDA MRTP-приказ: 200, `application/pdf`, 753 983 байта, 20 страниц, разобрано 2, текст настоящий, и обрезка названа местом — `[PDF text truncated at page 2 of 20: 18 page(s) not included; character cap 4000]`. HTML-путь не тронут (example.com как был).

## R58 — browser_body: настоящий корень и что осталось

Корень жалобы «отвергает любой id, а в ошибке чужой счётчик» — не парсер и не движок: `sidecar.js` отправляет кадр как `{...payload, id}`, где `id` — **корреляционный id протокола**, он затирает `id` запроса из payload. В Python доходили 65/66/67 — номера кадров. Правка обоюдная: поле переименовано в `requestId` на обеих сторонах. Коллизия в `sidecar.js` при этом остаётся латентной: любой op, чей payload несёт `id`, будет искажён тем же способом.

В движке: `request_body` принимает и CDP-id, и порядковый `#n`; два разных текста ошибки — «сессия пересоздана» против «вне окна захвата», с текущим диапазоном; документная запись закреплена от вытеснения из кольца и помечена в листинге; `requests()` отдаёт `captured/oldest/newest`. Попутно найден тихий дефект: nodriver называет поле типа `type_`, поэтому колонка типа в листинге была пустой всегда.

Замерен независимо: example.com — две записи, тип заполнен (`document`, `script`), `#1` резолвится. Тело не получено, и это отдельный дефект глубже: `Network.getResponseBody` на этом Chromium отвечает `-32000 No resource with given identifier found` для всех проверенных запросов, теперь это честно возвращается в `bodyNote`. Заголовки в том же вызове пришли пустыми — не проверено.

Поправка к R40: `reset=True` срабатывает на старте сессии, а не на каждой навигации, поэтому «this navigation» в текстах ошибок фактически означает «эта сессия».

## R60 — тела ответов получаются через Fetch-перехват (закрыто)

Network-домен отдаёт тело, только пока вкладка держит ресурс, поэтому после навигации был `-32000` всегда. В установленной nodriver есть второй, отдельный `get_response_body` — в `cdp/fetch.py:362`, и он законен только для запроса, стоящего на паузе на стадии Response. `RequestPattern` несёт `request_stage`, по умолчанию `Request`; в enum — `RequestStage.RESPONSE`, не `.Response`.

Схема: Network остаётся первой попыткой; при промахе вооружается `fetch.enable` с паттерном на точный url известной записи, запрос переигрывается (документ — повторной навигацией, подресурс — `fetch()` из контекста страницы, только GET), тело читается из paused-состояния, запрос отпускается `continue_response` на всех путях через `finally`, `fetch.disable()` всегда в `finally`, жёсткое окно 12 с, обработчик снимается.

Замерено независимо живьём, через сам инструмент: `#1` на example.com вернул настоящий HTML (577 байт, обрезан по капу) с честной пометкой, что это переигранный запрос. На github агентом получены script 25 345 байт и document 577 148 байт; после закрытия окна сеть течёт нормально, медиа-блок в силе; искусственное исключение внутри обработчика не оставило висячего запроса, перехват не залип.

Недоступно: ответы из memory cache рендерера (Fetch их не видит, окно просто истекает), не-GET записи, записи с url, усечённым до 300 символов; тело — лучшее для данного URL, а не байт-в-байт оригинал; повтор документа перезагружает вкладку и теряет DOM.

## R61 — повтор документа: настоящий виновник не устаревший Tab

`Tab.get(url)` в nodriver переходит на первую вкладку браузера и переподключается к ней, из-за чего меняется идентификатор CDP-сессии, а включённый `Fetch` остаётся на старой сессии. Отсюда `Invalid InterceptionId` при третьем подряд повторе. Замена на `tab.send(cdp.page.navigate(url))` убирает причину; повторное получение вкладки через `update_targets()` осталось как страховка. Замер: три повтора документа подряд — все по 1 025 950 байт, вкладка жива, `evaluate` отвечает.

Тело теперь ограничивается до декодирования: полный размер считается по длине base64, декодируется только первый кусок `4·⌈4·limit/3⌉` символов. Для тела ~1 МБ при капе 200 символов раскодировано 1068 символов. Ограничение протокола остаётся: `Fetch.getResponseBody` гонит тело целиком по websocket, и nodriver разбирает его как JSON целиком — обрезка возможна только после этого.
